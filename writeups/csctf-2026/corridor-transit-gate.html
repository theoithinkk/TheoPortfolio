Corridor Transit Gate

The trick

The gateway and the backend disagree on what a path means. The gateway's allow/deny ran on a slightly different normalization of the URL than the backend's router used to dispatch it. "..%2f" is the sweet spot: the gateway doesn't decode %2f (so it never sees the /internal/ segment and allows the request), but the backend does decode and collapse it (so it routes straight to the emergency-override handler). The front-end JS handed over the exact endpoint and body — the whole challenge was defeating that one boundary control. Defensive takeaways (API security / GRC angle): - Never enforce access control on the raw/formatted URL at a proxy while a separate component does the routing. - "Internal only" by network/path is not authentication. The emergency override should require a real identity - Don't ship privileged endpoints and payloads in client-side JS. 01Start point: the host and a downloaded OpenAPI spec (api_specification.json).

  • What I found: public routes for corridor status/assess, consignments, telemetry, and clearance/request. GET /api/v1/consignments shows CTLD-FR-8821 as HELD_AXLE_WEIGHT_DISCREPANCY at CP-04. The docket says the measured 46,200 kg exceeds the 40,000 kg viaduct limit, so the public POST /api/v1/clearance/request returns 403 ERR_AXLE_WEIGHT_DISCREPANCY: "Clearance must be authorized via internal dispatch controller."

02Pivot: where is the override? It is not in the public spec.

  • What I found: the portal docket page /portal/consignment/CTLD-FR-8821 has a "Supervisor Dispatch Override" button wired by a JS chunk at /static/assets/js/chunks/chunk-dispatch-admin.9c4d.js. That chunk hard-codes the hidden route and payload: POST /api/v1/internal/dispatch/emergency-clearance with {"consignment_id","reason"}, and the success response carries a clearance_token.
  • The catch: the edge gateway (Server: CTLD-Gateway, Go-ReverseProxy) returns 403 GW_ACL_INTERNAL_ROUTE_PROHIBITED for anything under /api/v1/internal/*, "restricted to authorized intranet nodes." So a legit supervisor on the intranet can click the button; an external client cannot.

03Pivot: profiling the gateway ACL (what did NOT work).

  • Source spoofing: X-Forwarded-For / X-Real-IP / X-Client-IP / True-Client-IP / CF-Connecting-IP (loopback and private ranges), trusted Host/node headers — all 403.
  • Rewrite headers: X-Original-URL / X-Rewrite-URL on an allowed path — ignored.
  • Provenance: X-Requested-With: XMLHttpRequest, Origin, Referer of the docket — all 403.
  • Hidden JSON fields on the public clearance (emergency/override/force/role/...) — ignored; it only checks the measured weight.
  • Boundary probing showed the ACL rejects the decoded path segment "internal" (e.g. intern%61l -> 403), and the backend does NOT decode %2f into a path separator (corridor%2fstatus -> 404).

04Pivot: path-normalization discrepancy between gateway and backend (the bypass).

  • The gateway rejects a literal "/internal/" segment but leaves %2f encoded; the Go backend decodes "..%2f" to "../" and then collapses the dot-segment. So putting an encoded parent-ref before "internal", behind a real decoy sibling, is seen by the gateway as a path under /api/v1/corridor/ (allowed) and by the backend as the internal route: POST /api/v1/corridor/..%2finternal/dispatch/emergency-clearance
  • Why the obvious variants failed: literal "x/../internal/..." gets collapsed by the gateway too (403); "%2finternal" (encoding the slash) is kept encoded by the backend and doesn't route (404). Only the mix "..%2f" — encoded enough to dodge the gateway, decodable enough for the backend — hits both targets.
