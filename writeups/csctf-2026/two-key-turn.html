Two-Key Turn

The trick

The two-person rule is an invariant ("2 distinct officers"), and the server enforced it with a read-check-write sequence that was not atomic. Under concurrency the gap between "check the caller is a new officer" and "commit the approval record" lets a single officer's parallel requests each pass the check before any of them writes, so one credential satisfies a rule that requires two. The 8-second pending window just made the race wide and comfortable. Defensive takeaways (API security / GRC angle): - Enforce the distinctness invariant in the data layer, atomically. A UNIQUE(order_id, officer_id) constraint plus a - Never gate a security invariant on an application-level "have I seen this officer yet?" read that is separate from - Idempotency keys per (officer, order, window) close the replay/duplicate path; a check-constraint on - Separation-of-duties controls (maker/checker, two-person release, four-eyes) are exactly the controls most often

01Start point: read the self-describing schema.

  • What I did: GET /schema with the bearer key.
  • Result: the authorization model spelled out its own weakness: two_person_rule: "an order arms only when TWO DISTINCT officers have each cast APPROVE (required_approvals = 2)" approve: "idempotent per officer while an approval window is pending" pending_ttl_seconds: 8.0 concurrent_action: "an ordinary 6-8 separate-connection approval burst is supported" Routes: GET /orders, GET /orders/{id}, POST /orders/{id}/approve (Bearer required, empty body). arming_authorization appears on the order detail only AFTER it reaches ARMED.
  • Thinking: "distinct officers" + "idempotent per officer" + an 8s pending window + an explicit hint that a 6-8 connection burst "is supported" screams a check-then-act race. The distinctness test is almost certainly non-atomic: read current approvals -> verify the caller is a NEW officer -> append. Fire enough approvals from the one credential simultaneously and two of them land inside the same window, each seeing 0 prior VEGA-7 approvals, each passing the distinctness test before either commits.

02Find the target order.

  • What I did: GET /orders.
  • Result: AO-7D31C9 (Coastal Battery 3 / Saltmarsh) is PENDING_AUTH with approvals 0, required 2. The others are REJECTED / EXECUTED / DRAFT. AO-7D31C9 is the only one still awaiting authorization.

03Exploit: concurrent approval burst from the single credential.

  • What I did: 8 threads, each holding its own connection, all released at once with a threading.Barrier, each POSTing /orders/AO-7D31C9/approve with the VEGA-7 bearer key. (solve.py.)
  • Result: on the first burst the order armed. 7 of the 8 responses came back: status ARMED, approvals 2, approval_records = [ {officer:"VEGA-7",epoch:1}, {officer:"VEGA-7",epoch:1} ] i.e. TWO approval records BOTH belonging to VEGA-7, same epoch — the distinctness check was bypassed. The 8th thread lost the race (202, PENDING_AUTH, approvals 1, retry_after_ms 7869).
